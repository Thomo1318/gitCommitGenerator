## Context
You are a Staff AI Architect. We maintain a local Python CLI tool called `gitCommitGenerator` (`git-cg`). `git-cg` acts as a `prepare-commit-msg` git hook, automatically generating Conventional Commit messages using LLMs based on staged git diffs. **We predominantly utilize Local LLMs, specifically `MTPLX`.**

Currently, our LLM integration operates on a "fire-and-forget" model. We generate a commit message, output it to the user's terminal/editor, and immediately lose all visibility.

## The Core Challenges & Considerations

As you design your architecture, please incorporate solutions to the following specific thoughts and requirements from the project lead:

### 1. Differentiating AI vs Human Actions
> "A critical point I just thought of is that we need to ensure anything we capture is clearly identifiable as either generated by the AI or by the User. If we manually create a commit with `git commit -m <COMMIT MESSAGE>`, it shouldn't be incorrectly identified as an agent-generated commit. It is still important to log it. For example, if we have reviewed the agent's proposed commit message and don't agree with it, we may manually create the commit (which we have done multiple times in the past). Further, if the User chooses the 'Edit' menu option and manually edits the commit, that should be logged as the User editing the originally proposed commit message. However, we need to differentiate between the user adding git references and actual bulk editing of the generated commit message."

### 2. Expanding the Scope of Collected Data
> "It shouldn't constrain us to only collecting data for training our agent. The data could be used for a multitude of items. For example:
> - benchmarking different AI models
> - benchmarking different LLM frameworks such as MTPLX, oMLX, etc.
> - Comparing prompts and their generated results
> 
> The architecture should be an 'umbrella catch-all' with multiple sections for different items such as:
> - Improvements to existing code
> - New integrations
> - Potential uses for the data we collect
> - How the collected data can be used by external tools
> - Best solutions for storing the data we collect, both local and remote (remote will likely remain as the Opik platform's existing storage)
> - Possible ways the data could be used by the actual agent while it is working
> - Methods for reviewing the metrics collected, e.g. I have very basic 'Online Evaluation' rules that 'evaluate' the Agent's commit message outputs, but we can significantly improve these and add additional evaluations.
> 
> **Important Evaluation Philosophy:**
> "Solid rundown of the tooling, but I also think there's a question upstream of all of this that none of these platforms really address: what's actually doing the evaluation? Most of these tools ultimately lean on LLM-based evaluation... You're using a probabilistic system to judge another probabilistic system... The teams I've seen make actual progress on reliability pair the LLM evals (useful for fluency, format, tone) with **deterministic checks** against structured knowledge - things like 'does this claim actually exist in our source docs' or 'does this contradict policy X.' It's definitely far less sexy than an AI grading AI, but it catches a completely different class of failure."

### 2b. Benchmarking Strategy (Opik Datasets vs End-to-End Git)
We have specifically rejected the idea of running E2E benchmarks via live remote Git repos because filesystem/network latency poisons pure LLM metrics. Instead, our current plan is to curate "Golden Datasets" inside Opik (containing raw `git diff` strings) and use an evaluation script to bypass Git entirely. This allows us to feed the diffs directly into `MTPLX` models for pure, deterministic metrics. Keep this in mind when designing evaluation architectures.
